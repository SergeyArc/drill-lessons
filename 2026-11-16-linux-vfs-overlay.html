Как слои становятся файловой системой

Почему один и тот же образ на vfs занимает десятки гигабайт, а на overlay — почти ничего поверх общей базы · ~12 минут

Сценарий серии. Тот же узел и задача CyberGym. В уроке 1 образ скачался и распаковался в store. Теперь вопрос: когда из слоёв собирается файловая система контейнера, сколько это стоит места — и почему твой бокс занимал 10–60 ГБ, хотя образ куда меньше.

Границы примера. Docker / containerd, драйверы vfs и overlay. Здесь — что драйвер делает со слоями на диске. Почему внутри gVisor overlay не поднимается и форсится vfs — урок 4. Делится ли база между разными store и узлами — урок 3.

1. Слои есть — кто делает из них файловую систему

Слои в store лежат, но контейнеру нужен один цельный корень /. Собирает его драйвер хранилища (storage driver). И тут есть два способа — от него зависит, сколько места уйдёт.

vfs — копировать всё. Самый простой драйвер: умеет только обычные папки и копирование. Каждый следующий слой он делает как новую папку, куда скопирован весь предыдущий слой плюс своя добавка. Контейнер при старте копирует результат ещё раз.

образ из трёх слоёв на vfs:
  слой 1:     файлы A
  слой 2:     копия A + B
  слой 3:     копия A + копия B + C
  контейнер:  ещё одна копия A, B, C

файл A физически на диске 4 раза, хотя контейнеру нужен один

Отсюда и твои числа: образ бокса маленький, а на диске он размножен по слоям. На практике так 33 слоя объёмом 3,22 ГБ занимали 116 ГБ, а бокс — 10–60 ГБ.

overlay — положить сверху. Нижние слои лежат один раз и общие (lower), а сверху тонкая папка для правок (upper). Базу целиком не копируют: контейнер смотрит в общие нижние слои, а своё пишет в свой upper.

тот же образ на overlay:
  lower (общие нижние слои):  A, B, C   ← один раз, читают все контейнеры
  upper контейнера 1:         пусто      ← своя тонкая папка
  upper контейнера 2:         пусто

Поэтому второй контейнер того же образа почти ничего не добавляет — своя пустая папка правок. Это твой спайк: первый Pod +3,8 ГиБ, следующие два — по ~1,3 МиБ.

vfs

Копирует всё дерево предыдущих слоёв в каждый новый слой и в контейнер. Ничего не делит. Сам Docker считает его непригодным для обычной работы — это запасной драйвер.

overlay

Держит нижние слои в одном экземпляре, общие для всех контейнеров; каждому контейнеру — свой тонкий верхний слой под изменения.

Открытый вопрос — вслух
Один и тот же образ запускают двумя контейнерами. Сколько места добавит второй контейнер на vfs и сколько на overlay — и почему разница?
На vfs второй контейнер — ещё одна полная копия всего дерева образа, то есть примерно столько же, сколько первый. На overlay нижние слои общие и уже лежат, второй контейнер добавляет только свой пустой верхний слой — почти ничего. Разница в том, что vfs копирует базу каждому, а overlay её делит.

2. А что при правке файла: copy-up

На overlay нижние слои только для чтения. Что будет, если контейнер меняет файл, который лежит в нижнем слое? Его нельзя править на месте — и драйвер делает copy-up: копирует этот файл целиком в верхний слой и дальше правит уже копию. Нижний слой остаётся нетронутым.

было:   lower: bigfile (1 ГБ, только чтение)
правим один байт в bigfile
стало:  lower: bigfile (1 ГБ, цел)
        upper: копия bigfile (1 ГБ) ← сюда легла правка

Копируется весь файл, не изменённые байты. Правка одного байта в файле на 1 ГБ кладёт в верхний слой весь гигабайт. Поэтому место под изменения считается по размеру тронутых файлов, а не по объёму самих правок — важно, когда задача пишет или пересобирает крупные файлы.

новый файл

Создаётся сразу в верхнем слое — копировать нечего.

правка старого

Сначала copy-up всего файла из нижнего слоя в верхний, потом правка копии.

Открытый вопрос — вслух
Контейнер на overlay дописал одну строку в конфиг размером 500 МБ из нижнего слоя. Сколько примерно добавится в верхний слой и почему?
Около 500 МБ: при первой записи в файл из нижнего слоя overlay копирует его целиком в верхний слой (copy-up) и правит уже копию. Отводится место по размеру файла, а не по размеру дописанной строки.

3. Как по диску понять, какой драйвер

Ошибок как таковых нет — есть поведение диска. Режим владения здесь: не настроить драйвер, а заметить по симптому, что собрано неверно.

Что видно на дискеО чём это говорит
Место под образом кратно больше суммы его слоёвСлои копируются, а не делятся — это vfs (нижние слои не общие)
Каждый новый контейнер того же образа добавляет ещё столько жеБазу копируют на каждого — vfs, либо у контейнеров раздельные store (это урок 3)
Первый контейнер образа дорогой, второй и третий — почти бесплатныНижние слои общие — это overlay работает штатно
Правка небольшого объёма, а диск вырос на гигабайтыcopy-up крупных файлов: тронули большой файл из нижнего слоя

Проверка: посмотреть размер store против суммы слоёв образа и как он растёт с каждым новым контейнером. Растёт линейно числу контейнеров — общей базы нет.

Открытый вопрос — вслух
Образ задачи — 3,8 ГБ. Запустили пять боксов, store занял под 190 ГБ. Что это за драйвер и по какому признаку ты это понял?
Это vfs (или раздельные store у боксов): 190 ГБ ≈ пять полных копий образа — база копируется на каждый бокс, а не делится. Признак — место растёт кратно числу боксов, а не остаётся около одного размера образа плюс мелкие правки, как было бы на общем overlay.

Источники

  • VFS storage driver — Docker Docs — vfs не использует copy-on-write: при создании слоя делается глубокая копия, расход диска большой и производительность низкая; для продакшена не рекомендуется.
  • OverlayFS storage driver — Docker Docs — нижние слои общие и read-only; при первой записи в файл выполняется copy_up этого файла в верхний слой; операция на уровне файла, не блоков.
