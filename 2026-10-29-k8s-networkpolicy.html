1. Цепочка: от записи до пакета

NetworkPolicy — объект в API, то есть только описание правила. Пакеты он не фильтрует. Чтобы правило заработало, нужны ещё два звена: программа на каждом Node, которая читает политику, и правила в ядре этого Node, по которым ядро проверяет каждый пакет.

Важное следствие из спецификации: пока Pod не выбран ни одной политикой, ему можно всё. Как только хоть одна политика выбрала Pod, он изолирован: проходит только то, что политики явно разрешают.

Пример: база данных принимает соединения только от API

Pod db (10.2.2.3) на Node 2. Pod api на 10.1.1.2 и 10.2.2.2. Pod песочницы на 10.1.1.3.

  1. Ты применяешь NetworkPolicy: «Pod с меткой app=db принимают входящие соединения только от Pod с меткой app=api».кто: kube-apiserver · где: API, etcd · меняет: только запись; на Node ничего
  2. Контроллер политик на каждом Node следит через API за политиками и Pod и видит новую политику.кто: контроллер kube-router в K3s · где: каждый Node · меняет: пока ничего
  3. Он переводит метки в адреса: app=db → 10.2.2.3, app=api → 10.1.1.2 и 10.2.2.2. Ядро меток не знает, ему нужны IP. Адреса api контроллер кладёт в ipset — набор «разрешённые источники».кто: контроллер · где: ядро Node · меняет: содержимое ipset
  4. Он пишет правило iptables в свою цепочку: «пакет к 10.2.2.3: источник из набора — пропустить, иначе — отбросить».кто: контроллер · где: ядро Node · меняет: правила фильтрации
  5. Песочница 10.1.1.3 шлёт пакет к db. Пакет доходит до Node 2, и ядро проходит цепочку: источника нет в наборе — пакет отброшен. Входящие правила срабатывают на Node получателя, исходящие — на Node отправителя.кто решает: ядро Node 2 · контроллер в пути пакета не участвует
  6. Pod api пересоздан с новым IP. Контроллер видит это через API и меняет только содержимое ipset. Правило iptables остаётся прежним.кто: контроллер · меняет: набор адресов

Как проверить: исполнением, в обе стороны. Соединение из песочницы к db должно не пройти, а из api — пройти. То, что kubectl показывает политику, ничего не доказывает. Только одна сторона тоже не доказывает: «не проходит ничего» выглядит как работающая политика.

Открытый вопрос — вслух
Для NetworkPolicy в K3s: кто действует, где, что меняет и как проверить результат?
Ты создаёшь запись в API. Контроллер политик на основе kube-router на каждом Node читает её, находит IP Pod по меткам, кладёт их в ipset и пишет правила iptables. Пакеты проверяет ядро Node: входящие на Node получателя. Проверка — попытка соединения из запрещённого Pod (не проходит) и из разрешённого (проходит).

2. ipset и цепочки — коротко

Это делегированный слой: синтаксис не нужен. Нужно понимать, что это, чтобы читать то, что сгенерировал агент, и видеть, где ошибка.

ipset

Набор адресов в ядре, на который ссылается правило фильтрации. Правило говорит «источник из набора X», а сам набор контроллер обновляет при смене IP Pod. Поэтому на каждый Pod не нужно новое правило.

Цепочка iptables

Упорядоченный список правил, который ядро проходит для пакета в определённой точке его пути: при входе, при пересылке, при выходе. Правила проверяются сверху вниз, первое совпавшее с итоговым действием («пропустить» или «отбросить») решает судьбу пакета.

Контроллеры складывают свои правила в собственные цепочки с узнаваемыми именами. У kube-router они начинаются с KUBE-ROUTER, у kube-proxy — с KUBE-. По этим именам видно, чьё правило перед тобой.

4. Молчаливые поломки

ЧтоЧто видно в APIЧто на самом деле
Нет исполнителя (Flannel один, K3s с отключённым контроллером)политика создана, ошибок неттрафик не фильтруется
Агент или контроллер упал на одном Nodeполитика есть, остальные Node в порядкеправила на этом Node перестают обновляться; что будет с новыми Pod, зависит от реализации — проверяют соединением
Опечатка в метке в политикеполитика созданаона не выбирает ни одного Pod, никто не изолирован
Надежда на NamespacePod в разных NamespaceNamespace — группировка в API, сеть он не изолирует

Во всех четырёх случаях сигнал один: API доволен, а поведения нет. Для песочниц это хуже падения: падение видно сразу, а открытая сеть — только когда агент уже сходил, куда не должен.

Открытый вопрос — вслух
Почему для кластера песочниц политика без исполнителя опаснее, чем Pod, который не стартовал?
Pod, который не стартовал, виден сразу: события, статус, нет результата прогона. Политика без исполнителя ничего не сообщает: kubectl её показывает, прогоны идут, а песочница видит внутренние Service кластера. Ошибка обнаружится, только когда ею уже воспользовались, поэтому работу политики проверяют исполнением.

Метафора, если помогает: политика — список «кого пускать», вахтёр — контроллер на Node, турникет — правила ядра. Без вахтёра список висит на стене, и все проходят.

7. На сессии

Без подсказок, вслух.

  • Проведи цепочку для политики «песочницы не ходят в kube-system»: на каждом звене — кто, где, что меняет.
  • Случай: в K3s политика запрещает песочнице выход к внутренним Service, но агент в песочнице до них достучался. Где искать причину, по порядку?
  • Проектирование: как в платформе песочниц убедиться, что политики работают, до первого прогона и после каждого обновления кластера?
