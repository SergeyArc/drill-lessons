Путь пакета в k8s

Кто прокладывает сеть Pod, что такое Service и где меняется адрес · ~15 минут

Границы примера. Flannel в режиме host-gw, kube-proxy в режиме iptables, обычные Pod (не hostNetwork), Service типа ClusterIP. В других режимах детали отличаются — они отмечены по месту.

1. Кто что делает

Объект в API — запись желаемого состояния. Он хранится в etcd и сам ничего не делает. Делает исполнитель: программа на Node следит за записями через API и меняет настройки ядра своего Node.

Объект в APIИсполнитель и где работаетЧто меняетКак проверить
Podkubelet, на каждом Nodeчерез containerd запускает контейнеры, создаёт namespaces и cgroupsсобытия Pod, статус контейнеров
Servicekube-proxy, на каждом Nodeправила DNAT в ядре: адрес Service → адрес одного из Podобращение к имени Service из Pod
сеть Pod (объекта нет)CNI plugin: при создании Pod его вызывает containerd, а агент CNI работает на каждом Nodeveth-пара, адрес Pod, маршруты к подсетям других Nodeобращение Pod → Pod на другом Node по IP

Отсюда класс дефектов: объект есть, исполнителя нет — API отвечает «создано», а поведения нет. Ошибки никто не покажет, поэтому проверяют исполнением, а не тем, что показывает kubectl.

Service ≠ CNI plugin

CNI plugin прокладывает сеть: даёт Pod адрес и связь с другими Node. Service — запись «имя и адрес → группа Pod». Pod может ходить к Pod по IP вообще без Service.

Service ≠ kube-proxy

Service описывает маппинг, kube-proxy заранее записывает его в ядро, а подменяет адрес само ядро. Так же, как конфиг nginx и процесс nginx. В пути пакета kube-proxy нет.

Чей адрес у Service

В режимах iptables и nftables адрес Service не висит ни на одном интерфейсе: он существует только в правилах DNAT. В режиме IPVS kube-proxy вешает адреса Service на служебный интерфейс kube-ipvs0. У headless Service адреса нет совсем: DNS сразу отдаёт адреса Pod.

Два overlay

OverlayFS — слой записи контейнера поверх слоёв образа. Overlay network — сеть Pod поверх сети между Node: пакет Pod заворачивается в пакет Node, обычно в формате VXLAN. В host-gw overlay нет.

veth-пара — два связанных виртуальных интерфейса: что вошло в один, вышло из другого. Один конец лежит в network namespace Pod и называется там eth0, второй остаётся на Node и подключён к bridge. Так изолированный Pod получает выход наружу.

Открытый вопрос — вслух
Чем Service отличается от kube-proxy и от CNI plugin? По одному предложению на каждого.
Service — запись в API: имя и постоянный адрес для группы Pod. kube-proxy — программа на каждом Node, которая превращает эту запись в правила DNAT в ядре. CNI plugin — то, что даёт Pod адрес и связь с Pod на других Node; Service опирается на эту сеть, но ею не является.

2. Путь пакета

Два Node в одной сети. Flannel выдал каждому Node свой диапазон адресов Pod: Node 1 — 10.1.1.0/24, Node 2 — 10.2.2.0/24. По IP Pod видно, на каком Node он живёт.

  1. Pod 1 шлёт пакет на 10.2.2.3. Адрес не из его подсети, поэтому пакет уходит на шлюз 10.1.1.1.кто решает: ядро внутри Pod, по маршруту по умолчанию
  2. eth0 Pod → veth111 → br0.veth передаёт кадр, bridge коммутирует по MAC (L2)
  3. Кадр адресован шлюзу, то есть самому Node, поэтому br0 отдаёт его в сетевой стек ядра Node 1.br0 одновременно коммутатор и интерфейс хоста с адресом 10.1.1.1
  4. Ядро смотрит в таблицу маршрутов: 10.2.2.0/24 via 192.168.1.2 — отправить на Node 2 через eth0.кто решает: ядро Node 1; маршрут записал агент Flannel (flanneld)
  5. Пакет идёт по реальной сети как есть, с адресами Pod. Конверта нет — это и есть host-gw. Поэтому Node должны быть в одном сегменте сети.
  6. На Node 2 ядро видит: 10.2.2.0/24 — своя подсеть за br0. Этот маршрут появился сам, когда br0 назначили адрес.кто решает: ядро Node 2
  7. br0 узнаёт MAC адреса 10.2.2.3 через ARP и отдаёт кадр в veth222 → eth0 Pod 2.L2, по MAC
  1. Pod 1 обращается к db. DNS кластера отвечает адресом Service 10.96.0.10. Пакет уходит на шлюз 10.1.1.1.кто: CoreDNS, затем ядро внутри Pod
  2. eth0 Pod → veth111 → br0 → сетевой стек ядра Node 1. Пока всё так же, как в соседней вкладке.
  3. DNAT на Node 1. Сразу при входе пакета в ядро, до выбора маршрута, правило меняет 10.96.0.10 на адрес одного из Pod за Service, например 10.2.2.3. Pod выбирается случайно, правилами с вероятностью.кто меняет: ядро (netfilter); правило заранее записал kube-proxy
  4. Дальше — ровно путь из соседней вкладки: маршрут на 192.168.1.2 → Node 2 → br0 → veth222 → Pod 2.кто: ядро Node 1 и Node 2, по сети, которую проложил CNI plugin
  5. Node 2 не знает, что адрес был от Service. На ответе ядро Node 1 по записи о соединении меняет адрес отправителя обратно на 10.96.0.10.

DNAT меняет адрес. Маршрут выбирает дорогу. Сначала одно, потом другое, и оба делает ядро Node отправителя.

Граница kube-proxy и CNI на этой линии: до DNAT включительно — правила kube-proxy, после — сеть, которую проложил CNI plugin.

Молчаливые поломки. Выключена пересылка пакетов (ip_forward) — пакеты в Pod других Node пропадают на Node отправителя без ошибок. Node стоят в разных сегментах сети — host-gw не доставит пакет, нужен VXLAN.

Открытый вопрос — вслух
Pod 1 на Node 1 обращается к Service, за которым стоит Pod 2 на Node 2. Назови по порядку все точки, где меняется адрес и где выбирается дорога, и кто это делает.
Адрес меняется один раз: на Node 1, сразу при входе пакета в ядро, DNAT по правилу kube-proxy меняет адрес Service на адрес Pod 2. Дорогу выбирает дважды ядро: на Node 1 по маршруту «10.2.2.0/24 через Node 2», на Node 2 по маршруту «своя подсеть за br0». Последний шаг — bridge по MAC отдаёт кадр в veth Pod 2.

5. На сессии

Без подсказок, вслух.

  • Без схемы перед глазами проведи пакет Pod → Service → Pod на другом Node. На каждом шаге: кто действует, где, что меняет.
  • Следствие: kube-proxy на Node остановили, CNI plugin работает. Что перестанет работать, а что продолжит?
  • Случай: Pod на одном Node видят друг друга, а между Node пакеты пропадают. Какие причины возможны и как отличить одну от другой?
