Таблица маршрутов

Куда ядро отправляет пакет и почему у каждого namespace своя таблица · ~12 минут

Сценарий серии. Хост, песочницы A (10.0.0.2) и B (10.0.0.3) в своих network namespace, veth к br0 (10.0.0.1). Новое в этом уроке: у хоста есть свой выход — eth0 с адресом 203.0.113.10, за ним шлюз провайдера 203.0.113.1 (адреса из диапазона для документации).

Границы примера. IPv4, одна основная таблица маршрутов на namespace. Схемы, где выбор таблицы зависит от правил (policy routing), — за пределами серии.

1. Что решает таблица маршрутов

Задача. Пакет попал в ядро — от процесса или с интерфейса. У него есть адрес назначения, и ядру нужно решить одно: в какой интерфейс его отдать и кому следующему. Это решение принимается по таблице маршрутов.

Три слова до начала

Подсеть и маска

10.0.0.0/24 — все адреса, у которых первые 24 бита (три первых числа) такие же: от 10.0.0.0 до 10.0.0.255. Число после косой черты — длина маски: чем она больше, тем уже и точнее подсеть. /32 — один адрес, /0 — все адреса вообще.

Шлюз

Машина в твоём L2-сегменте, которой отдают пакет для чужой сети, чтобы она отправила его дальше. Для песочниц шлюз — 10.0.0.1 на br0.

Таблица маршрутов

Список строк в ядре: «для такой-то подсети — отдать через такой-то интерфейс, и если нужно — через такой-то шлюз». Есть в любой Linux-машине и своя в каждом network namespace: она часть сетевого стека.

ЭлементКто ставитЧто решаетКак проверить
Строка своей подсетиЯдро само, когда интерфейсу назначают адрес с маской (10.0.0.2/24)Адресаты этой подсети — соседи по L2: отдать напрямую в интерфейс, кадр на MAC самого адресатав ip route строка с proto kernel и без via
Маршрут по умолчаниюТот, кто настраивает сеть: для песочницы — рантайм или его сетевой плагин, для хоста — система при подключении к сетиВсё, для чего нет строки точнее: отдать шлюзу. Кадр — на MAC шлюза, IP назначения в пакете прежнийстрока default via …
Выбор строкиЯдро при каждой отправкеЕсли адрес подходит под несколько строк, выигрывает самая точная — с самой длинной маской. default — это /0, он проигрывает любой другой подходящей строкекакая строка подходит под адрес и какая из них длиннее

Таблица выбирает только следующий шаг — интерфейс и, если нужно, шлюз. Весь путь до адресата не знает никто: следующая машина решает заново по своей таблице. Адреса в пакете маршрутизация не меняет (уменьшается только счётчик TTL, защита от бесконечных петель).

таблица маршрутов ≠ iptables

Таблица маршрутов решает, куда отправить пакет. iptables и nftables — что с ним сделать: пропустить, отбросить, переписать адрес. Это разные части ядра; правила netfilter стоят на пути пакета, но интерфейс не выбирают — урок 3.

маршрут ≠ DNAT

DNAT меняет адрес назначения в самом пакете. Маршрут адрес не трогает — только выбирает, куда пакет отдать по тому адресу, что в нём стоит. Подмена адресов — урок 4.

сосед ≠ шлюз

Соседу кадр идёт на его собственный MAC. Шлюзу — кадр на MAC шлюза, а в пакете всё равно адрес конечного получателя. Шлюз — не адресат, а следующий шаг.

маршрут ≠ изоляция

Маршрут говорит, куда пакет можно доставить, но не можно ли. Если на хосте есть маршруты к двум песочницам и включён ip_forward, хост перешлёт пакет из одной в другую. Запрещают это правила netfilter — урок 3.

Открытый вопрос — вслух
В таблице песочницы A две строки: 10.0.0.0/24 напрямую и default через 10.0.0.1. A шлёт пакет на 10.0.0.3 и на 8.8.8.8. Под какие строки подходит каждый адрес и какая выигрывает?
10.0.0.3 подходит под обе: под /24 и под default (/0 подходит под всё). Выигрывает /24 — маска длиннее, поэтому пакет идёт напрямую в eth0, кадр на MAC B. 8.8.8.8 подходит только под default — пакет отдаётся шлюзу 10.0.0.1, кадр на MAC br0, в пакете по-прежнему 8.8.8.8.

2. Две таблицы на одном пути

Так выглядит вывод ip route в namespace песочницы A и в namespace хоста. Колонки читаются так: подсеть · via — шлюз · dev — интерфейс · proto kernel — строку поставило ядро при назначении адреса · src — свой адрес на этом интерфейсе.

Песочница A
default via 10.0.0.1 dev eth0
10.0.0.0/24 dev eth0 proto kernel scope link src 10.0.0.2
Хост
default via 203.0.113.1 dev eth0
10.0.0.0/24 dev br0 proto kernel scope link src 10.0.0.1
203.0.113.0/24 dev eth0 proto kernel scope link src 203.0.113.10

eth0 у песочницы и eth0 у хоста — разные интерфейсы в разных namespace, совпадают только имена. Строка 10.0.0.0/24 dev br0 на хосте появилась сама, когда на br0 назначили 10.0.0.1/24: по ней хост знает, что песочницы — за br0.

  1. Процесс в A шлёт пакет на 10.0.0.3. Подходят обе строки таблицы A, выигрывает 10.0.0.0/24 — маска длиннее. Шлюза в строке нет: отдать в eth0 напрямую.кто решает: ядро в namespace A, по таблице A
  2. ARP за MAC B, кадр на MAC B уходит по veth в br0, br0 отдаёт его в порт vethB — всё как в уроке 1.bridge, по MAC
  3. B принимает пакет. Таблица маршрутов хоста в этом пути не участвовала: кадр не был адресован хосту, его переслал bridge.
  1. Процесс в A шлёт пакет на 8.8.8.8. Подходит только default via 10.0.0.1: отдать шлюзу через eth0.кто решает: ядро в namespace A, по таблице A
  2. Кадр на MAC br0 (шлюза), в пакете — 8.8.8.8. br0 видит свой MAC и передаёт пакет IP-стеку хоста (урок 1).
  3. Хост сначала смотрит: это мне? 8.8.8.8 — не адрес хоста. Значит, пакет чужой и его надо переслать дальше — это разрешено, только если в namespace хоста включён ip_forward. Выключен — пакет молча отброшен.кто решает: ядро хоста, по ip_forward
  4. Пересылка разрешена — таблица хоста. 8.8.8.8 подходит только под default via 203.0.113.1 dev eth0: отдать шлюзу провайдера через eth0 хоста.кто решает: ядро хоста, по таблице хоста
  5. Кадр на MAC шлюза провайдера, в пакете по-прежнему 8.8.8.8 — и адрес отправителя по-прежнему 10.0.0.2. Дальше решает таблица шлюза провайдера. Почему ответ на 10.0.0.2 не вернётся и что с этим делают — урок 4; какие правила стоят на этом пути — урок 3.

Каждая машина и каждый namespace решает по своей таблице и только следующий шаг. A решила «шлюзу 10.0.0.1», хост — «шлюзу провайдера через eth0». Чтобы хост вообще взялся за чужой пакет, нужен ip_forward.

microVM без bridge (продолжение строки из урока 1): на хосте вместо общей подсети за br0 стоит строка «адрес гостя → dev tap0». Хост маршрутизирует пакет прямо в TAP, коммутатор не нужен — в сегменте всего два конца.

Так на Firecracker-платформе: у каждого запуска свой namespace и своя подсеть /30, общего bridge нет. На хосте есть обратный маршрут к подсети каждого запуска и включён ip_forward — по маршрутам хост переслал бы пакет из запуска в запуск. Изолирует их не маршрутизация, а цепочка forward с policy drop в namespace каждого запуска.

Открытый вопрос — вслух
Пакет уходит с твоего VPS на 8.8.8.8. Кто решает, через какой интерфейс он уйдёт, и участвует ли в этом iptables?
Интерфейс выбирает ядро VPS по своей таблице маршрутов: под 8.8.8.8 подходит только default, значит — шлюзу провайдера через внешний интерфейс. iptables дорогу не выбирает: пакет проходит точки, где стоят его правила, и они могут его отбросить или переписать адрес, но решение «куда» принимает таблица маршрутов.

3. ip_forward и молчаливые поломки

ip_forward — настройка ядра: пересылать ли между интерфейсами пакеты, адресованные не этой машине. По умолчанию выключена: обычный компьютер не должен работать маршрутизатором. Настройка относится к сетевому стеку того namespace, который пересылает: в нашем сценарии — namespace хоста.

доставка ≠ пересылка

Пакет на 10.0.0.1 адресован самому хосту — ядро отдаёт его процессу на хосте, ip_forward не нужен. Пакет на 8.8.8.8 хосту не адресован — это пересылка, и без ip_forward она молча не происходит.

Молчаливые неисправности. Ошибок при запуске нет — видно только поведение. Это подсказки, что проверить.

Что видноЧто может быть и что проверить
A видит B, но не видит ни шлюз, ни интернетв таблице A нет маршрута по умолчанию — проверить таблицу внутри namespace A, а не на хосте
A видит B и 10.0.0.1, но не интернетна хосте выключен ip_forward: до хоста доставка работает, пересылка — нет. Другие причины (правила, NAT) — уроки 3–4
в песочнице только loopback, наружу ничегонет внешнего интерфейса: ломается на поиске маршрута — строки для адреса просто нет
пакет из A уходит с хоста, ответ не приходитотправитель 10.0.0.2 — приватный адрес, снаружи до него нет маршрута. Это не ошибка таблицы — урок 4
Открытый вопрос — вслух
На хосте выключен ip_forward. Почему A по-прежнему достаёт до 10.0.0.1, а до 8.8.8.8 — нет?
10.0.0.1 — адрес самого хоста: пакет доставляется хосту, пересылка не нужна. 8.8.8.8 хосту не принадлежит: пакет надо переслать в другой интерфейс, а без ip_forward ядро чужие пакеты не пересылает и молча их отбрасывает.

Источники

  • ip-route(8) — default равен 0/0; via — адрес следующего маршрутизатора; proto kernel — маршрут поставлен ядром при автонастройке.
  • ip-address(8) — noprefixroute: не создавать автоматически маршрут для подсети добавленного адреса; без флага он создаётся.
  • fib_trie — документация ядра — поиск маршрута ищет самый длинный подходящий префикс (longest matching prefix).
  • ip-sysctl — документация ядра — ip_forward: «Forward Packets between interfaces», по умолчанию 0 (выключено).
  • network_namespaces(7) — у каждого network namespace свои таблицы маршрутов и правила фильтрации.
